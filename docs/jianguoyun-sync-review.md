## 3. 详细问题

### SYNC-001：时钟偏差导致两端永久不一致

位置：

- `src/memo_app/sync/store.py:189-205`：以 `time.time()` 生成本机修订。
- `src/memo_app/sync/store.py:223-237`：本机写入无条件替换当前实体版本状态。
- `src/memo_app/sync/store.py:472-483`：按 `(rev_ts, writer_id, rev_seq)` 比较新旧。
- `src/memo_app/sync/engine.py:174-183`：拒绝比较键较小的远端修订。

复现：

1. A 的模拟时钟比 B 快 100 秒，A 新增记录并同步。
2. B 拉取记录后，再进行一次正常本地编辑。
3. B 上传，随后 A、B 交替执行 4 次同步。
4. A 仍显示原内容，B 显示后来的编辑内容。

原因：B 的后续修改虽然因果上更新，墙钟版本却小于 A 已有版本；
A 拒收 B 的修改，B 又不会重新应用已经拉取过的 A 的批次。
这不仅是并发编辑时丢掉一方，而是顺序修改也不能收敛。

修复方向：

- 按原计划实现父修订/因果版本，不用墙钟决定覆盖。
- 如产品明确选择 LWW，仍需保证新本地修订在逻辑上晚于已观察版本，
  并设计稳定的冲突与收敛规则；仅在相同时间戳下比较序号不够。

验收：两端时钟前后偏差、时间回拨、接收顺序变化后，顺序修改能传播，
重复同步最终收敛；并发修改按已确认的产品规则处理。

### SYNC-002：数据库执行故障导致记录永久漏同步

位置：

- `src/memo_app/sync/engine.py:139-172`：捕获 `sqlite3.Error` 后视为坏操作跳过。
- `src/memo_app/sync/engine.py:128-134`：随后推进该 writer 的应用进度。
- `src/memo_app/sync/service.py:269-283`：成功提示没有突出 `bad_ops`。

复现：A 上传一条记录，在 B 应用该记录时注入一次
`sqlite3.OperationalError("interrupted")`，随后撤销注入再同步。

结果：

```text
第一次：pulled=1，applied_ops=0，bad_ops=1
第二次：pulled=0，applied_ops=0，bad_ops=0
B 的记录列表：仍为空
```

原因：数据库执行失败不一定意味着远端数据无效。
当前逻辑却记录该修订并跳过，又推进游标；故障解除后没有重试机会。
界面还可能显示“已同步”，掩盖漏记录。

修复方向：

- 将纯输入校验与数据库执行分开，不把所有 SQLite 异常归类为坏数据。
- 可重试执行故障必须回滚且保留待处理状态，不推进成功应用进度。
- 无效数据若需隔离，也必须可追踪、可诊断，不能静默丢弃。
- 批次原子性与进度提交保持一致，有失败或隔离项时不能报完全成功。

验收：分别在提交前后、单条写入中、批次中间注入故障；
解除故障后自动补齐，不丢数据、不重复执行业务副作用。

### SYNC-003：重启后没有周期自动同步

位置：

- `src/memo_app/sync/service.py:106-114`：创建周期定时器，但未启动。
- `src/memo_app/sync/service.py:171-177`：只有保存配置时启动周期定时器。
- `src/memo_app/sync/service.py:261-263`：启动回调只请求一次同步。

复现：用已保存 `sync_enabled=True` 的隔离配置构造 `SyncService`，
执行启动回调，检查周期定时器状态。

```text
enabled=True
startup_calls=1
periodic_active=False
```

影响：用户重启应用后，如果没有本地编辑、手动同步或重新保存设置，
启动同步之后可能一直收不到另一台电脑的新记录。

修复方向：初始化时根据已保存的启用状态恢复周期调度；
暂停、重新启用和退出时也要统一管理定时器生命周期。

验收：保存配置、退出、重新启动后，不打开设置也能自动拉取；
停用同步后，周期和防抖均不再触发网络请求。

### SYNC-004：运行默认测试会覆盖真实同步库密码

位置：

- `tests/test_sync_vault.py:83-116`：双设备测试直接调用 `service.run_job()`。
- `tests/test_sync_vault.py:126-145`：错误密码测试也先执行真实建库流程。
- `src/memo_app/sync/service.py:51-55`：建库/加入后持久化库密码。
- `src/memo_app/sync/credentials.py:8-11,79-80`：使用全局服务名和 `vault_password` 项。

验证方式：拦截凭据写入边界，运行相关两个测试。
测试通过，但捕获了 3 次对 `vault_password` 的写入尝试。
如果未拦截，Windows 安全存储可用时会覆盖正式应用使用的该项。

影响：用户按项目说明执行测试，可能把真实同步库密码换成测试密码，
造成随后正常同步无法解密。临时数据库目录不能隔离 Windows 凭据管理器。

修复方向：

- 测试默认注入内存凭据后端或完整 mock，禁止接触正式凭据命名空间。
- 同样隔离 QSettings、本地数据目录和网络访问。
- 如确需测试真实凭据后端，使用显式 opt-in、随机测试服务名和独立探针。
- 测试清理不得通过删除正式凭据项来补救，也不能假设旧值可以重建。

验收：执行完整测试前后，真实系统凭据和应用设置不变；
安全存储不可用时，普通测试仍能稳定执行。

### SYNC-005：忽略条件写的服务端会使已有日志被静默覆盖

位置：

- `src/memo_app/sync/engine.py:446-459`：PUT 成功即返回；只有 412 才读取并比较旧内容。
- `src/memo_app/sync/transport.py:302-317`：`create_only` 只是发送 `If-None-Match: *`。
- `tests/test_sync_transport.py:60-66`：现有假服务的 PUT 直接覆盖对象。

复现：在本地假服务预置同 writer、同序号但不同内容的 commit，
调用 `_upload_batch()` 上传新内容。服务忽略条件头，返回成功。

```text
old_commit_overwritten=True
engine_reported_error=False
```

适用边界：该问题已在“不执行条件创建的服务”上复现，
但没有连接真实坚果云验证其行为，不能据此断言坚果云一定会覆盖。
当前实现也不能宣称对不支持条件写的服务有可靠兜底。

修复方向：

- 在正式启用前实测所依赖的条件写语义，并明确支持的服务能力。
- 同路径出现不同批次时停止并报告，不覆盖既有对象。
- 若必须兼容不支持条件写的服务，设计并验证可行的唯一写入者、
  身份恢复和写入协议，不能只发送条件头然后假定服务执行。
- 写后回读不能撤销已经发生的覆盖，也不能替代并发条件创建保证。
- 假服务需同时覆盖支持条件写和忽略条件写两种行为。

验收：存在不同内容时不会破坏原对象；应答丢失可幂等续传；
复制数据目录、恢复旧备份和重复序号不会静默改写云端历史。

### SYNC-006：设置验证失败仍被视为保存成功

位置：

- `src/memo_app/settings_dialog.py:198-204`：调用 `_save_sync()` 后无条件 `accept()`。
- `src/memo_app/settings_dialog.py:206-261`：多处校验失败或凭据保存失败直接返回。

复现：勾选启用同步，账号留空，点击保存。

```text
错误提示：请填写坚果云账号
dialog_result=1，即 Accepted
```

影响：错误提示随窗口关闭而消失，用户以为已保存成功；其他校验或凭据错误也受影响。

修复方向：让保存返回明确成功状态，失败时保留窗口、显示错误并聚焦问题字段。
异步建库/加入还应区分“本地配置已提交”和“远端设置已成功”。

验收：账号缺失、ID 无效、密码不符合规则、凭据保存失败时窗口不关闭；
合法配置才进入下一步，不错误宣称远端已就绪。

### SYNC-007：原 UI 冒烟检查已出现回归

位置：

- `src/memo_app/settings_dialog.py:107-108`：新增页面直接读取 `controller.sync`。
- `ui_smoke.py:53-55`：`SettingsStub` 只有 `hotkey_display()`。
- `ui_smoke.py:363-368`：仍用该 stub 构造设置对话框。

复现：

```text
SettingsDialog(SettingsStub())
AttributeError: 'SettingsStub' object has no attribute 'sync'
```

本轮验证的是该设置页构造路径失败，不表示已执行完整 UI 冒烟脚本。

修复方向：更新隔离服务 stub 和测试接线，覆盖新增设置页；
创建真实服务的 UI 测试还需 mock 凭据/配置，并正确关闭工作线程。

验收：原 `ui_smoke.py` 在隔离环境完整通过；
新增同步设置用例、关闭窗口和退出检查通过，无真实账号、设置或凭据副作用。

## 4. 需求待确认：冲突保留还是 LWW

原计划要求基于修订关系识别并发，保留冲突分支，不静默覆盖。
当前协议文档“已知限制”写着 LWW 已获用户确认；现有对话中没有看到该确认，
但不能据此排除其他会话中存在新的决策。

本轮双客户端验证：A、B 离线修改同一条，随后同步，两端最终只展示 B 的版本，
没有冲突选择入口。这里不声称 A 的旧内容已从所有本地队列或远端历史物理消失，
问题是当前正常使用流程不能按原计划查看和处理该冲突。

需要产品方明确：

- 如未批准 LWW：实现父修订、并发分支保存和冲突解决 UI。
- 如已批准 LWW：将决策依据与限制写清，修正用户指南；
  当前比较的是修改时间而不是“谁后同步谁覆盖”。
- 无论采用哪种策略，SYNC-001 的顺序编辑分叉都必须修复。

## 5. 本轮验证范围与限制

已完成：

- 阅读同步存储、引擎、传输、加密、凭据、调度、设置和相关业务入口。
- 58 项现有测试通过；执行时使用临时数据，并拦截正式凭据读写。
- 两客户端验证时钟偏差与并发编辑。
- 注入一次 SQLite 执行异常，验证后续同步行为。
- 隔离 Qt 配置验证启动调度、设置校验及旧 stub 构造失败。
- 拦截凭据写入确认默认测试的副作用。
- 在忽略条件写的假 WebDAV 上验证已有 commit 覆盖。

未完成、不得宣称已通过：

- 真实坚果云账号的条件写、限流、分页及配额兼容性。
- 公司网络环境与两台真实 Windows 电脑端到端验收。
- 当前打包 EXE 的全部同步功能验收。
- 完整 UI 冒烟、同步 UI 截图与独立美观评分。
- 修复后的回归检查及独立代码复审。

本轮复现使用临时脚本和故障注入，没有将它们加入仓库测试文件。
接手 AI 应将对应情形补成持久化、可重复执行的回归测试。

**在 SYNC-004 修复前，不要无隔离地直接运行默认测试命令。**
测试数据目录与云端假服务的隔离不等于系统凭据已经隔离。

## 6. 建议修复顺序与发布门槛

1. 先修复 SYNC-004，建立不会触及真实凭据和设置的测试基础。
2. 确认冲突策略，修复 SYNC-001 与 SYNC-002，补双客户端及故障测试。
3. 修复 SYNC-005，完成真实测试目录的条件写能力验证及日志保护。
4. 修复 SYNC-003，覆盖重启、停用、重新启用和退出。
5. 修复 SYNC-006、SYNC-007，完成设置交互和完整 UI 回归。
6. 在明确授权的测试库完成真实双机同步，再进行原路径打包和 EXE 验收。

每次修复批次完成后，按用户规则安排全新的独立子 agent 审查；
修复后重新换 agent 复审，最多三轮，仍有问题则披露剩余风险。
本轮是主 agent 审查，不替代修复后的独立复审。

不得只以“现有 58 项测试仍然通过”判定可以发布；
新增故障用例、产品决策、服务兼容性和真实双机验证都要有对应证据。
